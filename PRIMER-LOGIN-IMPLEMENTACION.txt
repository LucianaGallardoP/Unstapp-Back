PRIMER LOGIN (RF-10 / RF-12 / RF-13) - GUIA DE IMPLEMENTACION PARA BACKEND
================================================================================
Autor: (equipo, sprint sin dev backend)
Objetivo: dejar el flujo de "primer inicio de sesion" funcionando de punta a
punta en la web deployada. Este documento explica QUE se agrego, COMO funciona
y QUE pasos faltan para darle funcionalidad real (poblar BD, SMTP real, link de
redireccion del front, deploy).

NOTA: todo lo descripto YA ESTA CODEADO Y PROBADO en local (contra PostgreSQL
real) y con envio de mail real (Gmail SMTP -> casilla de prueba). Lo unico
pendiente es configuracion de entorno (variables) en staging/produccion.


================================================================================
1. RESUMEN DEL FLUJO
================================================================================
El alumno ya existe "pre-empadronado" en la BD (simulando la base de la
universidad): tiene DNI, Nombre, Apellido, Telefono, Email y el flag
FirstTime = true, pero todavia NO tiene contraseña propia.

Paso a paso:

  1) El alumno ingresa su DNI en el front (RF-10).
     -> POST /api/auth/verify-first-time { "dni": "40111222" }

  2) El backend valida el DNI:
       - No existe                -> 404 "Alumno no encontrado"
       - Existe y FirstTime=true  -> 200 + genera token y ENVIA EL MAIL (RF-12)
       - Existe y FirstTime=false -> 409 "Este DNI ya se encuentra registrado"
         (ya hizo su primer login antes)

  3) El alumno recibe un mail con un enlace al front:
       {FRONT}/crear-clave?token=XXXXX   (token de un solo uso, vence en 10 min)

  4) El alumno abre el enlace, el front muestra "Contraseña" + "Repetir
     contraseña" (RF-13) y al enviar:
     -> POST /api/auth/set-initial-password { token, password, confirmPassword }

  5) El backend valida el token, hashea la clave (BCrypt), la guarda en la BD y
     marca al alumno como validado (FirstTime = false). Devuelve 200.
       - Token invalido / expirado / ya usado -> 401

  6) A partir de ahi el alumno se loguea normal con POST /api/auth/login.


================================================================================
2. ENDPOINTS NUEVOS (AuthController)
================================================================================

--------------------------------------------------------------------------------
POST /api/auth/verify-first-time
--------------------------------------------------------------------------------
Request body:
  { "dni": "40111222" }            (DNI: solo numeros, 7 u 8 digitos)

Respuestas:
  200 OK    -> { "message": "Te enviamos un enlace de registro al correo
                  asociado a tu DNI." }
               (ademas dispara el envio del mail con el token)
  404       -> { "statusCode":404, "code":"STUDENT_NOT_FOUND",
                  "message":"Alumno no encontrado." }
  409       -> { "statusCode":409, "code":"ALREADY_REGISTERED",
                  "message":"Este DNI ya se encuentra registrado." }

--------------------------------------------------------------------------------
POST /api/auth/set-initial-password
--------------------------------------------------------------------------------
Request body:
  {
    "token": "XXXXX",              (el que viene en ?token= del mail)
    "password": "MiClaveSegura123",       (minimo 8 caracteres)
    "confirmPassword": "MiClaveSegura123" (debe coincidir con password)
  }

Respuestas:
  200 OK    -> { "message": "Tu cuenta fue activada correctamente." }
               (clave hasheada y guardada, FirstTime pasa a false)
  401       -> { "statusCode":401, "code":"INVALID_OR_EXPIRED_TOKEN",
                  "message":"El enlace no es valido o ha expirado." }
  409       -> si el alumno ya estaba validado (defensa extra)
  400       -> validaciones de modelo (password corta, no coinciden, etc.)


================================================================================
3. COMO ESTA GUARDADO EL TOKEN (seguridad)
================================================================================
- Se genera un token aleatorio (32 bytes, base64 url-safe). Ese valor "crudo"
  viaja SOLO en el enlace del mail.
- En la BD se guarda unicamente el HASH SHA-256 del token (nunca el token en
  texto plano), con una expiracion (ExpiresAt) de exactamente 10 minutos y un
  flag Used.
- Al pedir un nuevo enlace, los tokens previos no usados del alumno se invalidan
  (solo el ultimo enlace es valido).
- En set-initial-password se hashea el token recibido y se busca un registro
  vigente (no usado y no expirado). Si no existe -> 401.

6. POBLAR LA BD CON ALUMNOS DE PRUEBA (Seeder)
================================================================================
Hay un seeder idempotente (no duplica si el DNI/email ya existe) en:
    Unstapp.Application/Seeding/StudentSeeder.cs

Siembra 6 alumnos con FirstTime=true y una clave placeholder (hash BCrypt de un
valor aleatorio, para que un login previo a la activacion falle limpio).

DNIs sembrados:
    40111222, 40222333, 40333444, 40444555, 40555666, 40666777
(emails @alumnos.unstapp.edu -> NO son casillas reales, sirven para probar
 los codigos 200/409/404, pero NO para recibir el mail real.)

ACTIVACION: el seeder corre SOLO si la config SeedStudents=true. Por defecto
esta en false (no siembra en cada arranque).

ALUMNO DE PRUEBA CON EMAIL REAL (para recibir el mail de verdad):
  Ademas de los 6, el seeder puede agregar UN alumno con un email REAL que
  configures, util para probar el envio:
    SeedStudents=true
    Seed__TestStudentEmail=tu-casilla-real@ejemplo.com
    Seed__TestStudentDni=40999000        (opcional, default 40999000)

  Tip para probar sin exponer una casilla personal: usar un correo temporal
  tipo YOPmail (ej. unstap@yopmail.com) y revisar la bandeja en yopmail.com.

IMPORTANTE: despues de sembrar, volver a poner SeedStudents=false (es idempotente
igual, pero conviene dejarlo apagado).

Como se ejecuta: al arrancar la app, despues de migrar, si SeedStudents=true ->
StudentSeeder.SeedAsync(...). (Ver Program.cs, bloque despues de Migrate()).

7. CONFIGURAR EL SMTP PARA ENVIAR CORREOS REALES
================================================================================
El servicio Unstapp.Infrastructure/Services/EmailService.cs funciona asi:
  - Si Email:Smtp:Host esta CARGADO  -> envia el mail real por SMTP.
  - Si Email:Smtp:Host esta VACIO    -> modo DEV: NO envia, solo loguea el
                                         enlace en los logs (util para probar
                                         sin SMTP).

Claves de configuracion (en appsettings vienen vacias a proposito):
    Email:From                -> remitente (ej. no-reply@unstapp.edu o tu Gmail)
    Email:FromName            -> nombre visible (ej. "Unstapp")
    Email:Smtp:Host           -> ej. smtp.gmail.com
    Email:Smtp:Port           -> 587
    Email:Smtp:EnableSsl      -> true
    Email:Smtp:Username       -> usuario SMTP
    Email:Smtp:Password       -> clave SMTP

NO poner las credenciales en appsettings.json (se commitearia el secreto).
Usarlas como VARIABLES DE ENTORNO del servicio.

--- Opcion A: Gmail (rapido para pruebas) ---
  1) Activar verificacion en 2 pasos en la cuenta de Google.
  2) Generar un "App Password" (16 caracteres) en:
       https://myaccount.google.com/apppasswords
  3) Usar:
       Email__Smtp__Host=smtp.gmail.com
       Email__Smtp__Port=587
       Email__Smtp__EnableSsl=true
       Email__Smtp__Username=tucuenta@gmail.com
       Email__Smtp__Password=<app-password-16-chars-sin-espacios>
       Email__From=tucuenta@gmail.com
       Email__FromName=Unstapp
  OJO: un App Password de Gmail da acceso completo a la cuenta. Para produccion
  conviene una cuenta dedicada o un proveedor transaccional (ver Opcion B).

--- Opcion B: Proveedor transaccional (recomendado para produccion) ---
  Brevo / SendGrid / Mailgun dan credenciales SMTP dedicadas y mejor
  entregabilidad. Ej. Brevo:
       Email__Smtp__Host=smtp-relay.brevo.com
       Email__Smtp__Port=587
       Email__Smtp__EnableSsl=true
       Email__Smtp__Username=<usuario-brevo>
       Email__Smtp__Password=<smtp-key-brevo>
       Email__From=<remitente-verificado>

NOTA: el envio se hace DENTRO del request de verify-first-time (con await). Si el
SMTP falla, el endpoint responde error en vez de 200. Si se quisiera que un fallo
de mail no corte la respuesta, habria que pasarlo a un envio en background.

8. LINK DE REDIRECCION DEL MAIL (coordinacion con el FRONT)
================================================================================
El enlace que se manda en el mail se arma asi:
    {Frontend:BaseUrl}{Frontend:CreatePasswordPath}?token={TOKEN}
Ej:
    https://unstapp.com/crear-clave?token=V86LHc5kpfrb-IpZVRxAv28TxeP9CxGIsS...

Configuracion (poner la URL del FRONT deployado, NO la del back):
    Frontend__BaseUrl=https://<dominio-del-front>      (ej. el front en Vercel/Netlify)
    Frontend__CreatePasswordPath=/crear-clave          (ruta de la vista RF-13)

QUE DEBE HACER EL FRONT en esa ruta (/crear-clave):
  1) Leer el query param ?token=... de la URL.
  2) Mostrar la vista de creacion de contraseña (campos password + repetir).
  3) Al enviar: POST /api/auth/set-initial-password con
       { token, password, confirmPassword }
  4) Si 200 -> mostrar pantalla de exito y hacer login automatico
     (POST /api/auth/login) o redirigir al login.
  5) Si 401 -> token vencido/invalido: avisar y permitir reiniciar el flujo.

(El back NO redirige; solo arma el link. La navegacion la maneja el front.)

9. CHECKLIST DE DEPLOY EN RENDER (staging / prod)
================================================================================
En Render las variables anidadas se escriben con doble guion bajo "__".

Variables a setear en el servicio:
  # Activar y sembrar alumnos (la 1a vez; luego poner SeedStudents=false)
  SeedStudents=true
  Seed__TestStudentEmail=<casilla-real-o-yopmail>
  Seed__TestStudentDni=40999000

  # SMTP real
  Email__Smtp__Host=smtp.gmail.com
  Email__Smtp__Port=587
  Email__Smtp__EnableSsl=true
  Email__Smtp__Username=<usuario-smtp>
  Email__Smtp__Password=<clave-smtp>
  Email__From=<remitente>
  Email__FromName=Unstapp

  # URL del front (para el link del mail)
  Frontend__BaseUrl=https://<dominio-del-front>
  Frontend__CreatePasswordPath=/crear-clave

Pasos:
  1) Mergear/deployar este codigo (la migracion se aplica sola al arrancar).
  2) Setear las variables de arriba.
  3) Redeploy. Verificar en logs: "[StudentSeeder] ... insertados".
  4) Probar en Postman: POST {base}/api/auth/verify-first-time {"dni":"40999000"}
     -> 200, revisar que llegue el mail.
  5) Tomar el token del mail -> POST {base}/api/auth/set-initial-password -> 200.
  6) Poner SeedStudents=false y redeploy (o dejarlo si se prefiere; es idempotente).

(La connection string de la BD se setea con ConnectionStrings__DefaultConnection;
Render normalmente ya la tiene configurada para el servicio.)
